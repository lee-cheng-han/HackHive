TurtleTalk – Product Requirements Document (HackHive 2026 Best Minority Hack)
Project Overview
Name: TurtleTalk – Indigenous Language Learning & Cultural Connection Platform
Description: TurtleTalk is a web application that helps Indigenous communities preserve and revitalize their languages and culture. It offers interactive lessons, real-time AI conversational practice, and community-contributed stories to bridge generational gaps. By integrating advanced AI/ML and optional hardware, TurtleTalk provides a personalized learning experience accessible even in remote areas. The goal is to strengthen cultural identity and knowledge through technology, empowering Indigenous users while showcasing a polished, impactful project.
Problem: Indigenous languages and knowledge are at risk of disappearing, eroding cultural identity and well-being. Indigenous peoples represent under 6% of the global population but speak over 4,000 languages – many endangered
. Every two weeks, an Indigenous language dies, and 50–90% may vanish by the next century
. This loss is linked to serious social impacts: suppression of native language harms self-identity and mental health; Indigenous youth with limited knowledge of their language are 6× more likely to experience suicidal ideation than those more fluent
. Preserving language is not just cultural – it’s vital for community health, self-esteem, and empowerment
. Many Indigenous communities also face barriers in education and connectivity, making it hard to access learning resources or share traditional knowledge. There is a pressing need for a solution that leverages technology to address language loss, educational gaps, and cultural disconnection in a respectful, effective way.
Solution: TurtleTalk addresses these challenges with a comprehensive platform that teaches Indigenous languages and shares cultural knowledge through cutting-edge technology. It provides an engaging curriculum (words, phrases, stories) co-created with community input, and uses AI at multiple layers to enrich learning:
An AI conversational tutor (powered by an LLM) allows users to practice dialogue in their Indigenous language, ask questions, or receive feedback in a human-like manner.
Speech recognition ML gives pronunciation feedback, helping users gain confidence speaking aloud.
Personalization AI adapts content difficulty to each learner’s pace, and can predict when to review material for better retention.
Text-to-speech generates natural audio in Indigenous languages (e.g. using ElevenLabs) so learners can hear authentic pronunciations and elders can share stories in audio form.
An optional hardware kit or offline server (e.g. a Raspberry Pi-based library) extends access to offline or low-connectivity communities, ensuring inclusivity.
By integrating these elements, TurtleTalk offers a realistic yet ambitious solution for a 36-hour build: a functional web app that showcases AI-driven features and meaningful impact. This project not only preserves language and culture (reinforcing identity and well-being
) but also demonstrates technical excellence – aligning with “Best Minority Hack” and even Best Overall criteria.
Technical Architecture
The TurtleTalk system follows a modern web architecture with distinct frontend, backend, AI/ML services, and an optional hardware layer for offline access. The design emphasizes modularity, scalability, and integration of multiple AI components, as shown in the conceptual system diagram below (frontend ↔ backend ↔ ML services, plus optional hardware). Overall System Design: Users interact with TurtleTalk through a web browser (or mobile web). The frontend sends requests to a backend API server, which orchestrates between the database and various AI/ML modules. External AI APIs (for NLP and TTS) are utilized where appropriate, alongside on-device or server-side ML models. The system is cloud-hosted for reliability (e.g. on DigitalOcean for easy deployment and scaling
), but can also run in a local offline mode with hardware support.
Frontend (Client): The client-side is a responsive web app (HTML/CSS/JavaScript) built with a framework like React for a dynamic, interactive UI. This layer handles the user interface for lessons, chat, quizzes, and displays of audio/visual content. It manages offline caching for core content so that some features work with limited internet. The frontend communicates with the backend via RESTful APIs or WebSocket (for real-time chat responses). Key responsibilities:
Render lesson content (text, images, audio) and record user inputs (text or voice).
Capture microphone input for speech practice and send to backend for analysis.
Provide a chat UI for the AI tutor, displaying AI responses seamlessly.
Handle local state (progress tracking, caching data) and gracefully degrade features if offline.
Backend (Server & Database): The backend is built with a robust framework (e.g. Node.js/Express or Python FastAPI) to handle application logic and integrate services. It exposes API endpoints for the frontend (user auth, fetching lessons, posting answers, etc.). The backend interacts with:
Database: A cloud-hosted database (e.g. MongoDB Atlas or PostgreSQL) stores user profiles, progress, content (lessons, vocabulary, community-contributed stories), and usage logs. A NoSQL DB is ideal for flexible content (storing multilingual text, media links, etc.), while SQL ensures relational integrity for user data – the final choice will depend on team familiarity. In either case, using a managed DB on a platform like DigitalOcean Managed Databases ensures reliability and quick setup
.
ML Services: The backend contains the integration logic for AI/ML features. For example, when the user submits a voice recording for pronunciation check, the backend invokes a speech-to-text or pronunciation ML service. It may call external APIs (like a Google Gemini LLM API
 for chat responses or ElevenLabs API for TTS
) and handle the response before sending it to the frontend. Some simpler ML models (like a custom recommendation model) might run on the server itself. The backend ensures these calls are authenticated and handles any needed data preprocessing (e.g., formatting a prompt for the LLM or normalizing audio data for analysis).
Business Logic: This includes the lesson progression rules, scoring of quizzes, tracking achievements, and moderation of any user-generated content. Security and privacy measures are enforced here (e.g., controlling access to certain community data, anonymizing any sensitive analytics).
AI/ML Pipeline: The project employs multiple AI/ML components in a pipeline fashion:
Conversational AI (LLM): For interactive practice, the backend uses an LLM (Large Language Model) to power a chatbot tutor. We plan to leverage the Google Gemini API (if available) to harness a state-of-the-art multilingual model
. The pipeline would take the user’s input (either text or transcribed speech), prepend a system prompt that instructs the LLM to respond as a friendly language tutor (potentially bilingual in English and the Indigenous language), and then call the Gemini API. The LLM’s reply is then returned to the frontend chat interface. We will design prompt templates and few-shot examples so the LLM can handle tasks like translation requests (“How do I say ___ in Mohawk?”) or role-play a conversation, staying accurate with cultural context. If the Gemini API is not accessible, we’ll fallback to an open-source model or OpenAI GPT-4 for the hack demo.
Speech Processing: For pronunciation feedback, audio from the user is captured via the browser (Web Audio API) and sent to the backend. We will use a speech-to-text model or API (e.g., Google Cloud Speech or Wav2Vec2 fine-tuned on the target language if available) to get phoneme information. The ML pipeline will compare the user’s pronunciation to an expected pronunciation. If possible, we might train a lightweight classifier or use DTW (Dynamic Time Warping) on audio features to score pronunciation. The backend then returns actionable feedback (e.g., “Your tone on the second syllable was a bit off, try making it longer”) in both text and via TTS audio. This pipeline may involve some quick fine-tuning or calibration with example recordings from native speakers to improve accuracy for the specific language. Given hackathon time, we will likely use existing ASR models and focus on analyzing results rather than building models from scratch.
Personalization & Recommendations: The user’s performance data (quiz scores, words they struggle with, frequency of practice) feeds into a simple ML model to personalize the experience. For instance, we might implement a collaborative filtering or clustering approach to suggest content (“Users who practiced these words also liked…”) or a predictive model to estimate the user’s proficiency level and recommend next lessons. Initially, this can be rule-based (if low quiz score on a topic, suggest review) and later enhanced by ML (e.g., a Bayesian Knowledge Tracing model or a small neural network that predicts probability of recall for each word, enabling spaced repetition scheduling). This component runs on the backend as part of the pipeline whenever the user completes an activity, updating their learning path.
Emotion/Engagement Detection (optional AI layer): An innovative layer we are exploring is using Presage’s Human Sensing SDK for real-time user state detection via the webcam
. This would allow TurtleTalk to gauge a learner’s focus and emotion during a session using just the camera (completely opt-in). For example, if the system detects signs of frustration or low engagement (e.g. the user’s facial expression shows confusion, or heart rate and focus level indicate stress), the app could proactively offer a hint or switch to a different activity. Presage provides clinically-proven tracking of vital signs, movement, and emotional cues through standard cameras
. Integrating this SDK into our pipeline means the frontend can stream video (or periodic images) to the backend or directly to the Presage API, and receive metrics like heart rate or focus level in real time. The backend can then adjust the UX accordingly (e.g., trigger a “take a break” popup or play a fun cultural trivia). This is a stretch feature for the hackathon, but we mention it to show how AI can personalize learning in a human-centered way (and align with Presage sponsor usage in the Accessibility & Wellness context
).
Data Management: All user data and content will be managed securely. Content like lesson text and audio files might be stored in cloud storage (e.g., DigitalOcean Spaces or AWS S3) with CDN support for quick delivery. User-generated content (such as recorded stories from elders or uploaded images) will undergo moderation (by the team or community volunteers) to ensure accuracy and cultural appropriateness before being broadly visible. We also plan for localization: the system architecture supports multiple languages by design – content is tagged by language, and the AI models chosen (Gemini, etc.) are capable of multilingual understanding
. This means TurtleTalk can be extended to other Indigenous languages in the future by adding to the database and retraining/adapting the ML models with new data.
System Diagram: In the absence of a visual here, imagine the flow:
User Device (Browser) → (HTTP/WS) → Web Server (Backend) → DB (user data, content)
Backend → (calls) → AI APIs (Gemini LLM, ElevenLabs TTS, etc.)
Backend ↔ Optional Hardware Server (if offline mode, sync data)
Backend → Frontend (sends AI results, content)
This architecture is designed for robustness and scalability, following a cloud-based three-tier model
. It ensures that even if one component (e.g., an external API) fails, the core app still functions (graceful degradation: e.g., if TTS fails, text is still shown). Each layer can be scaled or improved independently – for example, the AI components can be containerized and scaled on GPU instances if usage grows, without altering the frontend. The modular design also makes it realistic to implement within a 36-hour hack: we can build a functional vertical slice (frontend-API-ML) for core features and stub or simulate more advanced ones, allowing a compelling demo while having a clear path for extension.
Features and User Flow
Key Features
Interactive Language Lessons: Structured lessons teaching vocabulary, phrases, and grammar through text, images, and audio. Lessons are themed (e.g., greetings, family, nature, health) and include quiz questions or mini-games for engagement. Each lesson showcases an Indigenous cultural context (for example, a lesson on “Family” might include kinship terms and a short story about a traditional family gathering). Progress is saved so users can resume or review completed lessons anytime.
AI Conversational Tutor: A chat-based interface where users practice the language in free-form. The AI tutor (powered by an LLM) can play different roles – a friendly teacher, a conversation partner, or even a historical character (to make learning fun). Users can type or speak (via microphone) in either their language or English. The tutor understands and responds appropriately: e.g., if the user tries an Indigenous phrase, the AI replies in that language (with translation if needed), gently correcting mistakes. This feature provides instant feedback and practice beyond static lessons, making learning immersive.
Pronunciation Coach (Speech Feedback): Users can practice speaking by repeating words or phrases into the microphone. The app analyzes the recording with ML to determine pronunciation accuracy. The user receives feedback like a score or specific tips (“Your pronunciation of ‘ᐊᓂᔑᓈᐯᒧᐎᓐ’ was good, but try emphasizing the second syllable more.”). They can listen to the correct pronunciation (via a native speaker’s recording or a high-quality synthetic voice) and retry. This coach mode builds speaking confidence in a safe, private way.
Community Stories and Oral History: A section of the app features audio stories, legends, and songs contributed by Indigenous elders or community members. Each story has text transcripts in both the Indigenous language and English, allowing learners to read along. Users can click a line to hear it (leveraging text-to-speech if no recorded audio). This not only preserves oral heritage but also exposes learners to fluent speech, idioms, and cultural values. Users can mark favorites, and a future feature will allow some community-approved user submissions (with moderation).
User Profiles & Progress Tracking: Each user has a profile with their selected language/dialect, skill level, and goals (e.g., daily practice time). Progress (lessons completed, achievements earned) is displayed on a dashboard. The app awards badges for milestones (first conversation, 100 words learned, etc.) to motivate users. If users permit, profiles can display a cultural name or clan affiliation, to foster community identity. However, privacy controls allow anonymity or alias use, understanding some may not want personal info displayed.
Offline Mode (Content Download): For users in rural communities with limited internet, TurtleTalk offers an offline mode. Users (or community facilitators) can download packages of lessons and media when they have connectivity. The app can then be used with those materials entirely offline. Progress would sync back to the server when internet is available. This ensures continuity for learners who face connectivity gaps. (This feature is enhanced by the optional hardware deployment described later, which can serve content over a local network.)
Accessibility & UI: The interface design considers accessibility: support for syllabics or special characters used by the language, adjustable font sizes, and optional voice navigation (users can speak menu choices, etc.). It will also include a bilingual interface (English/French UI in Canada, plus the Indigenous language where possible for immersion). For users with visual impairments, screen-reader compatibility and high-contrast themes will be provided. The goal is to ensure elders (who may not be tech-savvy) and youth alike find the app easy to use.
User Flow
A typical user journey to illustrate how these features come together:
Onboarding: The user visits the TurtleTalk web app and signs up (or logs in). During onboarding, they select their Indigenous community or language (e.g., Ojibwe), and their approximate proficiency (“Beginner” or “I know some basics”). They are greeted by the app with a welcome message in both English and Ojibwe. A brief tutorial highlights key areas: Lessons, Chat Tutor, and Stories.
Lesson Progression: The user starts with Lesson 1: Greetings. The frontend loads the lesson content from the backend. It displays the first slide: a word (“Aaniin” – “Hello”) with an illustration of two people meeting. The user clicks a play button to hear it pronounced. The audio is fetched (either a recorded clip or generated via ElevenLabs API in a native-like voice). They repeat the word and proceed. After a few new words, a quick quiz pops up (“How do you say ‘Hello’ in your language?” with multiple choices). The user’s answer is submitted to the backend, which checks correctness and returns the result. Suppose the user selects wrong – the app shows the correct answer and maybe a tip or a short video of an elder explaining that greeting’s cultural context. The lesson continues to completion, and the user earns a “Greetings Rookie” badge, which the backend records.
Conversational Practice: Next, the user heads to the AI Tutor Chat. A prompt suggests: “Try having a conversation at a store.” The user types (or presses a mic button and speaks) “How do I ask for water in Ojibwe?”. The audio is transcribed by the backend and passed to the LLM (Gemini). The AI recognizes the user wants a translation and responds: “To ask for water, you can say: ‘Niminikwe ombi’ (I would like water).” It might also provide a cultural note or ask the user to repeat the phrase. The user then says in Ojibwe, “Niminikwe ombi,” practicing the phrase. The AI replies in Ojibwe with a follow-up question, or if it detects an error (via the speech analysis pipeline), it gently corrects the user. This interactive session continues, with the user effectively conversing with the AI entirely in the Indigenous language by the end of it. If at any point the AI’s answer is complex, the user can click “Explain” and the tutor will switch to English to clarify (using the LLM’s ability to summarize or simplify). The real-time nature of the chat and the voice integration (the AI’s replies can be spoken aloud using ElevenLabs for a truly conversational feel) makes this feature engaging and showcases powerful AI use.
Pronunciation Feedback: The user then switches to Pronunciation Coach mode to specifically practice challenging words. They select the word “Miigwech” (Thank you) from a word list. The app plays the reference audio. The user taps record and says the word. The backend’s ML compares it to the reference; within a second, the user sees a feedback display: a score (e.g., 7/10) and highlights indicating the consonant they pronounced too softly. Perhaps the app even visualizes the waveform or pitch contour vs. the ideal, for those interested. The user tries again, and their score improves. They are satisfied and the app praises them, maybe unlocking an achievement for improving a pronunciation score.
Community Content: Finally, the user visits the Stories section. They choose a story titled “The Teachings of the Turtle.” A video thumbnail shows an elder speaking in Cree (for example). The user can watch the 2-minute clip of the elder telling the story in Cree with English subtitles. Alternatively, if only text is available, the user can read it and click a speaker icon to hear it narrated by the app’s TTS in a warm voice. They learn a new cultural lesson from this story. They leave a reaction or comment (if enabled) thanking the storyteller (comments might be pre-moderated or only positive emoji reactions to avoid any abuse, ensuring it remains a safe space).
Wrap-up: Throughout the session, the user’s actions are tracked: lesson complete, chat usage, etc. On their Dashboard, they see progress: e.g., “You’ve learned 10 new words today!” and maybe a streak if they use it daily. The user logs off feeling accomplished. If this were a demo scenario, the presentation would highlight how each feature was powered by underlying tech (point out where AI responded, where voice was synthesized, etc., to impress judges with technical depth).
This flow demonstrates how a user seamlessly interacts with multiple features in TurtleTalk. For the hackathon demo, we would likely script a scenario like the above to show the judges the end-to-end experience: starting from onboarding, doing a quick lesson, having an AI chat, and hearing a story – all within a few minutes – to prove the product is functional, intuitive, and impactful.
Tech Stack Justification
Our tech stack choices balance rapid development (for a 36-hour hack) with scalability and alignment with sponsor technologies. Below is a breakdown of the stack and reasoning for each component:
Frontend: React.js (JavaScript/TypeScript) – Chosen for its component reusability and quick development of interactive UIs. React’s vast ecosystem (UI libraries, state management like Redux or Context API) lets us implement features like dynamic quizzes and chat interfaces efficiently. We’ll use HTML5 and CSS3 (possibly Tailwind or Material UI for styling) to ensure a responsive design. React is well-suited to building a single-page application that can offer offline capability via service workers (important for rural accessibility).
Backend: Node.js with Express – Node allows us to write server code in JavaScript, which speeds up development since our front-end is JS as well. Express is lightweight and perfect for creating REST APIs quickly. It can easily integrate with various SDKs (like Presage’s npm package if provided) and handle real-time needs using libraries like Socket.io (for live chat updates). Alternatively, we considered Python (Flask/FastAPI) especially if our ML components use Python. If we go with Python, we’d likely use FastAPI for its async support and easy integration with ML libraries (TensorFlow/PyTorch). The final decision may depend on team familiarity – we aim for whatever yields faster results in the hack timeframe. In either case, both Node and Python have abundant libraries for connecting to sponsor APIs and cloud services.
Database: MongoDB (NoSQL) – We favor MongoDB for storing the lesson content, user progress, and flexible data like community stories. NoSQL’s schema flexibility is beneficial because language content can vary in structure (some lessons might have different fields, stories have different metadata). We can embed user progress in user documents for quick retrieval. MongoDB Atlas offers a free tier and easy cloud deployment, or we could use a DigitalOcean Managed MongoDB which simplifies setup
. MongoDB also handles geospatial queries (if in future we tag content by region) and full-text search (useful for a dictionary feature).
Rationale: A relational DB (like PostgreSQL) is also viable especially for structured data like user accounts and could ensure ACID compliance for, say, financial transactions (not a major concern here). But given the hack context, avoiding complex migrations with NoSQL is a time-saver. If we need relational features (like joining user table with achievements, etc.), we might use a hybrid approach (Postgres for core user data, Mongo for content). However, to keep it simple, we lean toward one primary DB (Mongo) and handle any relations at the app logic level.
AI/ML Technologies: This is the heart of our tech stack, fulfilling the requirement of AI in multiple layers:
LLM (Large Language Model): We plan to utilize Google’s Gemini API (if available to hackers) for our chatbot tutor and possibly translation tasks. According to MLH, Gemini can understand language like a human and generate creative content
, making it ideal for building an AI that can converse and teach. If Gemini access is not provided, we will use OpenAI GPT-4 via API (since it’s a proven alternative) or a fine-tuned LLM on HuggingFace that we can host. The ease of an API for LLM (Gemini/GPT) is that we don’t need to train a model from scratch in 36 hours, but we still get powerful results. We will need to ensure our use complies with any usage limits (likely we’ll cache some responses or use short prompts to stay within free tier limits).
Speech Recognition & Analysis: For converting speech to text (STT) and analyzing pronunciation, we might use Google Cloud Speech-to-Text or Mozilla DeepSpeech/Coqui STT if offline. Using a cloud API like Google’s would save time on model training and likely handle the accent better, but it requires internet. An open-source model could be deployed locally (perhaps on a laptop with a decent CPU/GPU or on the cloud). Given time constraints, leveraging a well-documented API is safer. We also plan to use libraries like Praat or Librosa for audio analysis (e.g., extracting pitch, formants for more detailed feedback). The speech pipeline might involve multiple tools: e.g., use STT to get the spoken word, then compare phoneme alignment using something like Montreal Forced Aligner if possible. This stack is admittedly complex, but we will iterate a basic version (maybe only check duration and volume of speech as a proof-of-concept, then refine if time permits).
Text-to-Speech: ElevenLabs API will likely be our choice for generating spoken audio from text. ElevenLabs provides remarkably natural and emotionally expressive voices
. We can clone a voice that resembles an elder or simply use a default voice if available for the language (some Indigenous languages might not be supported natively, but we could use a similar sounding voice or an English narrator voice until we gather actual recordings). ElevenLabs is straightforward to call via REST and will add a “wow” factor by giving our app a voice (for narrations, pronunciations, or even the AI tutor speaking). If ElevenLabs integration works smoothly, we’ll definitely highlight it (also aiming for the sponsor prize)
.
Presage (Human Sensing): If we incorporate Presage’s SDK, it will be part of our tech stack to achieve the optional engagement detection. Presage is a cutting-edge tool to get vital signs and emotions via webcam in real-time
. The integration involves including their SDK (likely available for web or as a native module) and using their API calls to get metrics. We’d use it sparingly (maybe only during certain exercises or if user opts in, to avoid performance issues). The reason to include Presage is to align with the accessibility and HCI improvements it offers – for example, a contactless wellness check-in for a learning session
. While not critical to core functionality, it shows technical depth and our commitment to user well-being, which is a judging criterion (responsible AI use). We’ll use it if time permits, focusing on one key use (like focus detection to adjust lesson difficulty on the fly).
Custom ML (Personalization): We may implement a simple Python scikit-learn model or even use a small neural net (PyTorch/TensorFlow) for personalization. For example, a decision tree or logistic regression could predict whether a user will remember a word tomorrow based on their quiz answers today (for scheduling reminders). Given hack constraints, a heuristic or rules might stand in for ML initially, but we’ll design the system such that swapping in a trained model later is easy. If time allows, we might crunch some dummy data to train such a model (perhaps simulate user interactions).
Cloud Hosting & Infrastructure: DigitalOcean is our preferred cloud platform to deploy TurtleTalk. MLH offers $200 credits for DigitalOcean, which we can use to set up:
A Droplet (VM) or the App Platform to host our backend and database
. DigitalOcean’s simplicity will let us deploy directly from GitHub, speeding up continuous deployment. We also note that DigitalOcean has a new DigitalOcean AI (Gradient) service
 which provides GPU resources and even serverless ML endpoints. If our project needs to host an ML model (e.g., a fine-tuned language model or a speech model), we could containerize it and run it on a Droplet with GPU, or use Gradient’s offerings for quick model serving – enabling efficient ML inference without deep DevOps work.
CDN and Storage: We might use DigitalOcean Spaces (S3-compatible storage) to serve media (images, audio files) quickly to users globally. This improves performance and user experience (especially for remote communities with high latency; a CDN edge cache would help).
Scalability: Though our hack demo will have few users, using DigitalOcean means we can easily scale the app if needed (adding more Droplet instances behind a load balancer for the web server, or scaling the DB). This demonstrates we’ve thought of future growth – relevant if we pitch this as a real product that could go beyond the hackathon.
Frameworks & Libraries (Misc): We will leverage numerous open-source libraries to accelerate development:
Auth: Use something like Firebase Auth or Auth0 for quick user authentication (so we don’t spend time building login from scratch, and benefit from security best practices out-of-the-box).
UI/Design: Possibly use a template or UI kit for a clean design (time is short for custom CSS). We want a polished look to impress judges for “Best Overall,” so using a proven design system (Google’s Material or a Bootstrap theme tuned to an Indigenous aesthetic – maybe with earth tone colors, etc.) will help.
Map API (stretch): If we include any feature to connect users by region or display community locations, a map API (Google Maps or Mapbox) could be integrated. This is a stretch goal to show where stories or users come from, adding an empowerment angle (visualizing the breadth of Indigenous communities engaged).
Testing: While hack projects often forego tests, we’ll use tools like Postman to test our APIs and maybe write a few basic unit tests for critical functions (to ensure reliability since we want a stable demo).
In summary, our tech stack is a combination of web-standard tech (React/Node) for speed, AI APIs/SDKs for advanced functionality, and cloud services for deployment. Each choice is justified by either the need for rapid prototyping (e.g., using existing APIs vs. training new models) or by aligning with hackathon sponsor tools that give us an edge (using technologies like Gemini, ElevenLabs, DigitalOcean not only strengthens our project technically but also positions us for those sponsor prizes). By articulating these choices, we ensure that every team member and stakeholder (mentor or judge) understands how we plan to build this and that it’s feasible in the hackathon context.
ML/AI Use Cases
TurtleTalk leverages AI/ML in at least three major use cases to deliver intelligent features. Each use case is detailed below, including its purpose, the technical approach, and how it enhances the user experience:
1. AI Conversational Tutor (LLM-Powered Chatbot)
Use Case: A user engages in free-form conversation or Q&A with an AI that acts as a language teacher or partner. For example, the user might say, “Teach me how to introduce myself,” and the AI tutor will respond with a custom dialogue in the target Indigenous language, then guide the user through practicing it. AI/ML Technique: This feature is powered by a Large Language Model (LLM), such as Google’s Gemini or a comparable model. The LLM is prompted with a specialized instruction set to behave as a bilingual tutor: it has knowledge of the Indigenous language’s vocabulary and can explain concepts in English as needed. We will feed it a prompt that includes: a) context about the user (their name, level, etc.), b) the role (“You are a friendly Ojibwe language tutor”), c) examples (“If the user says X in English, respond with Y in Ojibwe and explain”), and then the user’s latest input. The model generates a response that ideally contains the Indigenous language phrase and some explanation. Technical Flow: When the user sends a message (text or voice) in the chat:
The backend ensures we have the text input. If voice, it’s transcribed via STT first.
The backend formats a prompt for the LLM. Example prompt snippet: “[System] You are an Ojibwe language tutor AI. Greet the user in Ojibwe. If they ask questions in English, answer in Ojibwe and then translate. Keep responses brief and encouraging.\n[User] How do I introduce myself?\n[AI]…”.
The LLM API (Gemini) is called with this prompt. Given Gemini’s capabilities (understanding language like a human)
, it should produce a contextual answer. Suppose it returns: “AI: You can say ‘Niin ___ nindizhinikaaz’ which means ‘My name is ___’. Now you try introducing yourself.”.
The backend receives the response. It might post-process if needed (e.g., ensure it’s safe, truncate if too long).
The frontend displays the response in the chat UI. It also might use TTS to read it aloud (especially the Indigenous phrase) so the user hears proper pronunciation.
The conversation continues turn by turn. The LLM’s state (conversation history) is maintained to provide context, so the AI remembers what was said (limited by token memory). If needed, we will truncate or summarize past dialogue to fit within token limits for the API.
Value to User: This use case transforms language learning from rote memorization to an interactive, immersive experience. The user essentially has a 24/7 personal tutor who can:
Answer questions in real-time (e.g., “How do I say ___?”).
Engage in dialogue, providing the much-needed practice partner for a language that the user might not have access to in their daily life.
Personalize responses: the AI can adjust based on user input complexity (we can prompt it to use simpler language if the user seems beginner, or more complex sentences for advanced users).
Provide cultural context or usage examples that static lessons can’t cover. For instance, the AI might share when it’s appropriate to use a phrase, or a short related cultural fact.
From a judging perspective, this use case demonstrates sophisticated AI integration – we’re not just calling a vanilla API, but crafting a purposeful application of an LLM (which aligns with the hackathon’s criteria of “AI-first with depth, beyond basic API calls”
). We will highlight that the AI is effectively functioning in two languages and adapting to the user, showcasing both technical complexity and social good (making language practice accessible). Feasibility: Using a pre-trained LLM via API is realistic within 36 hours. The main tasks are prompt engineering and perhaps fine-tuning with a small domain dataset (if we have access to one – e.g., a list of common phrases or a tiny parallel corpus for the language to improve accuracy). If needed, we could fine-tune a smaller model on a few example QA pairs we prepare, but that’s optional. We’ll focus on optimizing the prompts during development to get desirable behavior. We will also include some fallback hard-coded knowledge (like a small dictionary) for critical phrases, so if the AI fails or is inaccurate, the system can correct or verify the answer before showing it. This ensures the demo doesn’t produce any blatant mistakes in the Indigenous language (since judges might not speak it but we want to be culturally respectful and correct).
2. Pronunciation Evaluation and Feedback
Use Case: A user uses their microphone to practice pronouncing words or sentences in the Indigenous language, and the system evaluates their pronunciation, giving corrective feedback. For instance, a user says a word and the system responds, “Your pronunciation was 80% correct. You need to hold the ‘aa’ sound a bit longer.” AI/ML Technique: This involves speech processing and classification. The primary ML components are:
Automatic Speech Recognition (ASR): to convert the user’s speech to text (to confirm what was said). If the ASR can be tuned to the Indigenous language, it can also align the spoken input with the expected phrase.
Pronunciation Scoring Algorithm: There are a few approaches here. One is using the ASR’s confidence scores or word error rate as a proxy for pronunciation quality. Another is forced alignment: using a tool to align the audio to the known correct phrase and measuring timing differences or likelihood. A third approach is extracting acoustic features (MFCCs, pitch, duration) and comparing them to a native speaker’s reference.
Possibly a pre-trained speech pronunciation model (e.g., some language learning apps use models that output phoneme accuracy scores).
Given hack time, we likely use a combination of a cloud ASR and heuristic analysis:
We know the target phrase (from the lesson context, or if user chose a word to practice).
The user’s audio is sent to Google Cloud Speech API with language hint. It returns a transcript and maybe word confidence scores.
Compare the returned transcript with the target phrase. If the API mis-recognizes, that indicates pronunciation issues. For example, user said “miigwech” but ASR heard “miigwetch” or something off – we parse that difference.
Additionally, use Audio Analysis: measure duration of vowels, overall pace, maybe pitch contour. For languages with tone or length distinctions, this is important. We might simply compare the user’s audio to a reference recording using DTW (Dynamic Time Warping) to see similarity.
Based on these, we craft feedback. E.g., if the main error is at the second syllable, say that specifically. If overall confidence is low, suggest trying slower or listening again to reference.
Technical Flow: When the user submits a recording:
The frontend captures audio (likely 5-second clip max for a word/phrase) and sends it as a WAV/FLAC blob to the backend.
Backend calls ASR (with proper language code if available, or a custom model if we made one). If language is not supported well by cloud ASR (some smaller Indigenous languages might not be in Google’s models), we could attempt a phonetic model or at worst, allow the user to self-assess with provided reference.
Assuming we get a result, the backend runs a Pronunciation Scoring Module – our custom logic combining the methods above. For hack demo purposes, we might implement a simpler logic: for example, compute the Levenshtein distance between ASR result and correct phrase. Or even just flag which phonemes might be off if ASR gives phoneme time stamps.
The backend creates a feedback object: score (0-100 or 0-5 stars), and textual feedback. Possibly choose from a few templates (“Great try! Just a minor tweak on ___ needed.” / “Good effort, but you might need to practice the R sound.”).
The frontend displays this and optionally plays the reference audio again or a synthesized slow version of it for clarity.
Value to User: Pronunciation is one of the hardest parts of language learning, especially without a teacher. This ML feature acts as an automated pronunciation coach, giving users an affordable and instant way to know if they’re saying it right. The user can practice repeatedly in private, which is less intimidating than practicing with a fluent speaker. Over time, this can significantly improve their speaking ability and confidence. For Indigenous communities, getting the pronunciation right also shows respect for the language, and this tool helps learners honor that. From a tech perspective, this use case highlights AI for audio analysis – showcasing a different modality (speech) beyond text. It also can be tied to the Presage vital sign detection if we wanted: e.g., detect if user’s heart rate spikes when speaking (maybe indicating nervousness) and encourage them to relax, though that’s more a stretch idea. In any case, it demonstrates we’re using ML for more than just text generation; we’re doing signal processing and real-time feedback, which is complex. Feasibility: We will scope this carefully. At minimum, we can demonstrate this feature with a small set of words that we tune for. For example, we may only fully implement it for ~5 words in the demo (hard-code the expected and have precomputed some thresholds for what’s “acceptable” pronunciation by recording ourselves saying them correctly vs. incorrectly to generate sample data). This way the demo will definitely show a working pronunciation check. 3. Personalized Learning & Predictions (Adaptive Learning Paths)
Use Case: The app adapts to the user’s learning progress using AI predictions. For instance, after some interactions, the system predicts the user struggles with verbs more than nouns and reorganizes upcoming lessons to focus on verbs, or it predicts the user might forget a word they learned last week and prompts a review. This encompasses both real-time personalization and predictive analytics to keep the learner engaged and progressing efficiently. AI/ML Technique: This is essentially a recommendation/problem modeling task. We can draw from techniques in educational data mining:
Knowledge Tracing Models: like Bayesian Knowledge Tracing or Deep Knowledge Tracing, which predict the probability a student knows a skill after a series of practice opportunities.
Clustering/Profiling: Group users by learning style or errors made (e.g., cluster common pronunciation mistakes – maybe a cluster means the user’s first language influences their accent in a known way, so tailor feedback differently).
Collaborative Filtering: If we had many users, we could recommend content that helped similar users. In a hack, we simulate this logic by just having a predefined adaptation.
For the hack MVP, we implement a simpler predictive model: e.g., a spaced repetition scheduler using the Leitner system or an SRS algorithm to predict when a user will forget a word (this is effectively a prediction of memory decay using a formula). Another element is using user engagement data (time spent, which content they skip) to adjust difficulty – possibly using a decision tree to classify if a user is bored vs overwhelmed (some research uses response time and accuracy to infer this). Technical Flow:
The backend maintains a profile of each user’s performance metrics: scores, number of attempts per quiz, etc.
After each quiz or exercise, we run a function to update their mastery levels. For example, if they consistently score low on pronunciation, mark that skill as “needs work.”
The next time the user requests a lesson, the backend’s lesson selection logic uses the stored data and possibly a simple ML model. For demonstration, we might implement a rule-based engine (if score < 60% on last 3 quizzes, recommend an easier module next). To add ML flavor, we could train a classifier on synthetic data (we generate some hypothetical user profiles and what we’d recommend to them) – essentially training a model to mimic our expert rules.
Concretely, suppose the user struggled in Lesson 2 (vocabulary about family). The system could flag that. When the user is about to do Lesson 3, we insert an extra review segment with flashcards of Lesson 2’s key terms. If the user breezed through, maybe we fast-track them or unlock a bonus challenge to keep them interested.
Another predictive element: dropout/churn prediction. We could use metrics to guess if a user is likely to quit (e.g., if they haven’t logged in in a week, or they skip many things). Our system can then proactively send a nudge (“We noticed you haven’t practiced recently, here’s a cool new story added!”). This ties in AI by possibly using a logistic regression trained on usage patterns to predict probability of retention – aligning with general hackathon interest (and even sponsor challenges like the Fidelity one about predicting churn, though unrelated domain, but methodology similar).
Value to User: The personalization ensures users get a tailored experience, which is more effective and engaging than a one-size-fits-all app. It prevents frustration (by not repeatedly showing what they already know) and prevents discouragement (by revisiting things they found hard, but in a supportive manner). For Indigenous learning, this is key – everyone comes with different exposure (some might have heard the language from elders, others are starting fresh), so adaptation respects those differences. It also shows respect for the user’s time and goals (e.g., if someone is mostly interested in conversational phrases, the app can prioritize that). From a project perspective, this use case demonstrates that we are using AI not just for flashy features, but also for invisible UX improvements (the “smart” part of a smart tutor). It might not be as visually obvious in a demo as the chatbot or voice, but we can explain that under the hood an AI model is tracking progress and making decisions. This addresses the “multiple layers of AI” requirement by having something like a prediction model running in the background in addition to the front-facing AI features. Feasibility: We will implement a basic version for the hack. For example, hardcode two “profiles” and branch the demo: If user answers certain quiz questions wrong in demo, we simulate the system recommending a remedial action (perhaps show a message “Because you had trouble with X, we suggest reviewing Y”). We can also simulate time-based prompts by using test data. The full machine learning model (like training a neural network on user data) is not possible with no real data, but we can create a mock-up or use open data from education if any (some public EdTech datasets exist, though not specific to indigenous languages). In any case, implementing a rule-based personalization and labeling it as AI-driven (with the intention to refine it with actual ML later) is acceptable for now. 4. (Optional) Real-time Engagement Detection (Presage AI)
This use case is optional but worth mentioning as a unique AI angle: Use Case: While the user is using the app, the system monitors their face via webcam (with permission) to detect signs of disengagement or stress. If the user appears frustrated (e.g., furrowed brows, or an elevated heart rate indicating stress) during a lesson, the app responds empathetically – perhaps offering a helpful tip or switching to a lighter activity. Conversely, if the user is highly engaged or excited (smiling, leaning forward), the app provides positive reinforcement or maybe increases difficulty slightly since the user is ready. AI/ML Technique: This uses the Presage Human Sensing Layer. Presage’s SDK can output metrics like heart rate, breathing rate, focus level, and emotional state just through the camera
. The underlying ML involves computer vision and signal processing: analyzing micro-blush in the face for pulse, movement for engagement, facial expression recognition for emotion. We do not build these models ourselves (as Presage provides them), but integrating the API is an ML use because we must interpret its outputs with our app logic. Technical Flow:
The user would be asked to opt-in and turn on camera for “Focus Mode” or something similar. Perhaps this is only during practice sessions.
The frontend, using Presage’s JavaScript SDK (if available), starts the camera and streams data to Presage’s model (likely running locally or in cloud). We get a feed of metrics, e.g., “Focus: 60% (moderate), Emotion: Neutral, Heart rate: 90 bpm”.
The backend (or frontend script) interprets these. For instance, if focus drops below 50% for 10 seconds, it triggers an event “user distracted”. If heart rate jumps and facial expression is angry after a failed quiz attempt, trigger “user frustrated”.
Our application has a policy for these events: “user frustrated” might cause a pop-up: “It’s okay, that was a tough one. How about a hint?” with a button to show hint. “User distracted” might cause the app to gently ping “Are you still there? Let’s take a quick fun quiz to re-engage!” or even pause the lesson timer if we had one.
If positive engagement is detected (“user smiling”), we can give instant praise: an animation or confetti on correct answers to reward that moment of joy, reinforcing it.
Value to User: This is a novel feature bringing emotional intelligence to the app. It can help users feel seen and supported. In a sensitive context like revitalizing a language, learners might feel emotional (positive or negative) – having the app respond appropriately can improve retention. It’s like having a teacher who can sense when you’re bored or upset and adjusts their teaching style. This level of responsiveness can prevent users from giving up out of frustration and make learning more fun. From a technical standpoint, it’s an innovative integration that sets our project apart. It demonstrates we’re pushing the boundary of HCI by incorporating physiological computing. It directly aligns with Presage’s suggested use cases like “contactless wellness & fitness” and “accessibility” – monitoring stress to enhance user experience

Optional Hardware Layer
While TurtleTalk is primarily a web-based software solution, we have designed an optional hardware integration to further support Indigenous communities, especially those in remote or low-connectivity areas. This hardware layer is not essential for core functionality (the app runs fully in the cloud/web), but it enhances accessibility and sustainability of the solution in real-world community settings. Hardware Overview: The proposed hardware is a Raspberry Pi-based Offline Server kit, possibly with additional sensors or peripherals for capturing content:
A Raspberry Pi 4 (or similar single-board computer) acts as a local server and Wi-Fi hotspot. It can host the TurtleTalk web application and database offline, and users in a community can connect via Wi-Fi using their phones/laptops to access the app without Internet.
Preloaded Content: The Pi can store all lesson content, media, and even a pared-down AI model for local inference (if feasible). For example, an offline language model (maybe a smaller transformer or rule-based chatbot) could be deployed for basic Q&A if internet is down. At minimum, it serves the static content and could queue any user actions to sync when internet becomes available.
Solar Power & Battery (optional): In some remote areas, power is unreliable, so a small solar panel and battery setup can keep the Pi running. This idea is inspired by projects like SolarSPELL, which provided solar-powered digital libraries on Raspberry Pis to remote communities
. In fact, SolarSPELL has successfully deployed 597+ offline libraries, including empowering the Hopi Tribe with local health education resources
, which validates the approach for educational content delivery in Indigenous communities.
Input/Recording Device: To encourage elders or local teachers to contribute stories and words, the hardware kit can include a simple audio recorder or microphone connected to the Pi. This could be as straightforward as a USB microphone or even a custom “record button” device. With a press, it records audio and stores it on the Pi, tagging it for later integration (e.g., an elder could record a series of words or a short story, which the development team or community IT person can later upload to the main database). This lowers the barrier for contribution – elders might be more comfortable with a tangible button than navigating a web form.
Displays or IoT Elements (stretch): Optionally, the kit could include a low-cost tablet or an e-ink display that can showcase the word of the day or run a quiz in a community center without requiring personal devices. Another idea is an LED indicator that shows when the device is on or syncing, for transparency.
Integration with Software: The Raspberry Pi would run a local instance of the TurtleTalk backend and database. We would use Docker to containerize the app for easy deployment on the Pi. Users connecting to the Pi’s Wi-Fi (which has no internet passthrough, or limited satellite uplink) can open TurtleTalk in their browser as if online. The difference is, the Pi might not have the heavy AI services (since those need GPUs/Internet):
For chatbot: offline mode might restrict to preset dialogues or a small local model (if we have one for basic responses).
For speech: without cloud, we could still do simple recording and playback, but pronunciation scoring might be limited (unless we include some offline ML model like Vosk for STT).
Essentially, offline mode focuses on content consumption and practice with what’s stored.
When the Pi gets connectivity (maybe periodically via a cellular dongle or when someone brings it to a place with Wi-Fi), it can sync data:
Upload new user sign-ups or progress to the cloud main server (so if later they log in from a personal device online, they don’t lose progress).
Download any new content or updates (new lessons, updated AI model if available).
This sync can be managed by a small sync script or service.

More relevant might be a hardware like an Arduino kit for environmental sensing – not directly tied to language, but could be used in a lesson where you measure something (like weather or plants) and learn the words for those readings. That, however, might be beyond scope.

Stretch Goals
Given the limited 36-hour hackathon window, we focused on core features for our MVP. However, TurtleTalk has a lot of potential for expansion. Below are some stretch goals and future enhancements we envision if we had more time or for post-hackathon development:
Mobile App (Native): Develop native mobile applications (Android/iOS) for TurtleTalk. While the web app is mobile-responsive, native apps could work offline more robustly, send push notifications for practice reminders, and access device features like the microphone/camera with lower latency. A mobile app would increase accessibility, as many in remote communities use smartphones as primary internet devices.
Additional Indigenous Languages: Extend support to more languages and dialects. Our platform is language-agnostic by design, but it would require collecting content (word lists, recordings) for each new language. A stretch goal is partnering with communities to onboard, say, 5 languages across different regions. Each would have its own lessons and cultural content. We’d also need to fine-tune AI models for new languages (especially the pronunciation and any GPT prompting).
Community and Social Features: Add a community forum or social feed within the app where learners can ask questions and get answers from native speakers or teachers. Perhaps a feature to connect learners with mentors (like a matching system for language buddies) could be introduced. Gamification like leaderboards or group challenges (e.g., a “learn 100 words in a week” challenge among a class) could boost engagement as well.
Gamified Learning (Mini-Games): Implement more interactive mini-games for learning. For example, a game where you match Indigenous words to images under time pressure (reinforces vocab), or an AR scavenger hunt: use your phone camera to identify objects in your environment and learn what they’re called in the Indigenous language (this could use image recognition AI to detect the object, then fetch the word – a fun extension of ML use).
Augmented Reality (AR) Cultural Experiences: A creative stretch could be using AR to bring cultural artifacts or scenes to life. For instance, pointing your phone at a real object (like a type of plant or animal) and the app overlays the name and any cultural significance in the Indigenous language. Or use AR filters that teach traditional symbols or patterns with context. This would blend technology with culture in an engaging way, though it’s a hefty feature to develop.
Voice Recognition for Continuous Conversation: Improve the AI tutor to handle full-duplex conversation (speaking and listening simultaneously) more like a real voice assistant. This might involve integrating with a service that can do wake-word detection and streaming ASR so the AI can listen as it speaks. The stretch is to make practicing conversation as natural as talking to a friend, without needing to click buttons for each turn.
Curriculum Expansion & External Content: Collaborate with educators to incorporate a full curriculum that could be used in schools. This includes adding assessment tools (for teachers to track student progress), certification levels (beginner, intermediate, fluent certificates maybe tied into something like Duolingo’s model or CEFR levels adapted to the indigenous language context). Also, integrate external resources: e.g., link to dictionaries, or include news articles in the language for advanced practice (with AI summarization for learners).
Enhanced Personalization with ML: Train and deploy more advanced personalization models. For instance, use machine learning to adjust to learning styles – some people might learn visually vs. orally, etc., and the app could prioritize content format accordingly. Also, implement spaced repetition fully using algorithms like SM2 (from Anki) to schedule reviews at optimal intervals, improving long-term retention.
Data Sovereignty and Privacy Features: As we gather user data and language content, a crucial consideration (especially for Indigenous communities) is data sovereignty. A future goal is to allow communities to self-host their data if desired, perhaps through blockchain or secure federated servers. We could integrate encryption for sensitive cultural content and ensure the community leaders have control over what happens with the data (who can access, etc.). Though not a “feature” in the traditional sense, building tools for community admins to export or manage their community’s data would be a valuable extension.
Integrating Solana for Rewards/Economy: If not done in the hack, as a future feature we could create a reward economy. For example, users earn “TurtleCoins” for completing lessons, which could be tokens on a Solana blockchain. These could be redeemed for real merchandise from sponsors or simply serve as a fun incentive that has real ownership (with a crypto wallet). We could also explore using Solana smart contracts to support community fundraising or contributions – for instance, tokenizing contributions (each story contributed mints an NFT that acknowledges the contributor).
Multi-Modal Learning with Music and Art: Incorporate other cultural content like songs (with lyrics to learn language through music) or artwork (learn descriptions or stories behind art pieces). AI could be used to perhaps generate simple exercises around a song (fill in the blank lyrics) or even to generate images from text (like if a user writes a story in the language, use DALL-E/Stable Diffusion to illustrate it as a fun output).
Professional Integration: In the long term, integrate with platforms like Duolingo or education systems if possible. Perhaps TurtleTalk could become a specialized plugin for existing apps or be adopted by schools. That’s beyond hack scope but a direction to mention.
These stretch goals illustrate that TurtleTalk is not a one-off demo, but a concept with longevity and room for growth. In a hackathon report, listing them shows the judges we have a vision for the project beyond the weekend – that we understand the road to making this a truly impactful product and have many ideas to continue its development.
